# 中文公文 Skill Reference 重构当前架构

更新时间：2026-09-13。本文记录当前候选已经落盘的结构及仍需验证的边界，是维护索引，不是产品运行规则或完成证明。当前实现以 `chinese-official-writing/SKILL.md`、实际 references 和 scripts 为准；page map 与 route manifest 用于维护核对，不能替代真实文件和写稿验证。

## 一、当前主线

当前运行顺序是：

```text
用户需求拆解
→ 选择一个主文种页或事务主叶
→ 按任务信号叠加必要共性页、条件场景页
→ 执行成稿后的编号复核
→ 读取 delivery.md 交付
```

用户需求先拆为任务与交付件、稿件用途和主体对象、底稿与修改范围、篇幅与形式。随后依据用户模板、最新版底稿、明确标题和实际用途选择唯一主叶；`reference-index.md` 是常规索引，`genre-routing.md` 只在文种或行文关系冲突时辅助判定，兼容场景由其专门分流页处理。

起草、改写、压缩、审核和格式处理是同一文种上的任务动作，不是位于文种之前的一组独立首层页面。当前没有 `workflow-draft`、`workflow-edit`、`workflow-review-full` 等页面，也没有“交付模式页先于文种页”的运行链。旧 `workflow.md` 的有效动作已分别进入入口、信息选择、结构编辑、字段编辑和压缩等现有页面，文件本身已删除。

## 二、写稿、改稿和审稿的同文种衔接

- **写稿**：选定主文种或事务主叶后，读取 `information-selection.md`；办理要素、论证关系、短稿、格式或专门场景只有在相应信号出现时叠加。
- **改稿**：沿用同一主文种和最新版底稿，按实际动作加读 `structure-editing.md`、`field-editing.md`、`official-style.md` 或其他必要页。局部修改只检查改动及关联段落。
- **审稿**：仍先确定稿件所属主文种或事务叶，再叠加 `review-checklist.md`。只审时交付问题位置、风险和建议；审查并改稿时落实已确认问题并交付改后稿。

三类任务都接回 `SKILL.md` 的成稿检查顺序。现行编号复核依次为：有篇幅要求时运行 `draft_length.py`；用 `final-review-layers.md` 核对事实、状态、主体和文种；所有成稿、改后稿和审核任务读取 `anti-ai-patterns.md`，并在引文、数字、术语或校对要求出现时读取 `proofreading-checklist.md`；随后按 `prose-lint-usage.md` 运行 `prose_lint.py`；最后读取 `delivery.md`。文种页的专项核对不能成为提前交付出口。

## 三、五类规则页

“五类规则页”继续作为维护索引语义，按实际文件职责理解：

1. **文种页**：承担报告、请示/申请、通知、函、纪要、讲话、方案、制度、新闻等正文功能、骨架和本类状态边界。
2. **事务/场景页**：处理整改报告、反馈报告、意见建议、投诉反映、采购或其他稳定业务场景；有明确主文种时作为附加页，没有主文种的兼容材料才由专门事务主叶承担。
3. **写作流程页**：承担信息选择、办理要素、论证、结构、字段、压缩、语言和格式动作，不重新选择文种。
4. **复核流程页**：承担审核范围、事实与文种复核、抗 AI 味、校对和专项检查，不反向启动总路由。
5. **条件附加页**：只在稳定信号出现时补充算力、人物顺序、技术术语等能力，不替代主文种。

`reference-index.md`、`genre-routing.md` 和轻量任务卡是路由入口；`delivery.md` 和两个普通脚本是收束与执行工具。它们支持五类规则页，但不需要虚构成新的首层模式页。

## 四、单叶隔离协议

“单叶隔离协议”保留以下当前可执行约束：

1. 一项独立稿件只选一个必要主文种页或事务主叶；多份稿件逐份选路。
2. 共性页和条件附加页必须有当前任务信号，不因一个业务关键词加载相邻文种骨架。
3. 主叶负责本类功能，共性页负责跨文种动作；同一规则不在多页复制为不同强度。
4. 附加页和专项核对完成后回到入口既定步骤，不反向跳回总索引，不自行提前进入交付。
5. 事实、直接分析、未定状态和实质缺项保持边界；合理分析可以使用材料和常识直接支持的一层关系，不能借骨架补成既成事实。
6. 页面职责由正文和路由清单维护，不要求每个产品页增加 YAML 页头、`allowed_reads`、`forbidden_reads` 或其他尚未落地的构建契约。

讲话页仍同时覆盖讲话、致辞、演讲、主持开场和述职，完整主持词与书面述职需要不同骨架。该混杂尚未完成归属和实写验证，因此当前不能宣称所有文种均已实现单叶隔离。

## 五、路由清单

“路由清单”由两层组成：

- 产品内的 `reference-index.md` 给出常规用途的唯一主叶和条件加读页，`genre-routing.md` 只解决功能、行文关系及冲突。
- 维护区的 `maintenance/specs/reference-route-manifest.json` 记录页面、触发信号、主叶、附加页、复核页和停止信息；当前清单包含实际文件名，用于发现无关伴读、双主叶、循环和不可达页。

manifest 是维护快照，不是 Agent 每轮生成的交付模式清单，也不是“文件已列入即完成验证”的证明。其内容必须随当前产品文件校准；page map 中的 `rewrite`、`retain` 和 `delete` 仅表示架构处置，仍需结合逐页语义核验和真实写稿判断。

## 六、普通脚本与 Pro Hook

普通 MIT 产品当前保留两个相互独立的脚本：

- `chinese-official-writing/scripts/draft_length.py`：只在篇幅步骤按条件运行，提供正文计数。
- `chinese-official-writing/scripts/prose_lint.py`：在文稿复核步骤运行，提供确定性风险提示。

两者按不同阶段调用，不合并，也不具备 Agent 生命周期或强制交付门禁能力。Agent 仍需解释结果、处理已确认问题，并对修改后的相关内容复核。

Hook 核心、交付门禁、宿主适配和 `review_gate.py` 不在当前 MIT 产品入口或活动构建链中。保存资产位于 Pro 独立分支 `codex/pro-hooks-preserved-20260912@3b6f273b6ee4ea583e7c0ade8311ad1f262d7159`，状态与已验边界见 `maintenance/docs/pro-hooks-next.md`。保存分支的既有本地协议验证不能写成当前 MIT 已启用 Hook，也不能证明所有宿主生命周期已重新验证。

## 七、已建成与未验证

### 已建成

- 当前入口已经按“需求拆解 → 主叶 → 必要附加 → 编号复核 → delivery”组织。
- 常规索引、冲突路由、主文种/事务页、共性页、条件附加页、复核页和交付页均已有实际文件；旧 `workflow.md` 已移除。
- MIT 产品保留 `draft_length.py` 与 `prose_lint.py`，Hook 资产已与普通产品分离并可在 Pro 保存分支追溯。
- page map 与 route manifest 已建立，可用于继续核对职责归属和组合读取。

### 仍未验证或未闭合

- 全部旧规则的逐条语义归属、所有页面冷审和跨场景组合真实写稿尚未闭合。
- 当前候选尚未证明与基线全量等价，也未证明无候选独有硬回退；静态文件存在、字符减少或单叶通过都不能替代组合验证。
- 讲话页的主持/述职混杂仍待归属、路由和实写验证。
- 普通短稿、复杂稿、局部改稿、Word、脚本真实调用及正文/文后提示隔离仍需按当前 Spec 完成覆盖。

只有逐页语义、组合路由、真实写稿、脚本边界和正文洁净度均有匹配证据后，才能进入合并判断。
