# WR-027 投诉与情况反映专叶预登记

日期：2026-09-02。

## 起点与单一原子

固定基线为 `main@2d50fcd3c2d7449dfa5baf1a8f11e80da9c083c8`。候选只在 canonical `SKILL.md` 增加亲历方投诉、问题反映和情况反映的窄直达路由，新增一个共享文种叶，并从通用行文用语入口移除重复的情况反映路由词。首轮不修改 description、Hook、版本、通用事实边界或兼容镜像。

候选应稳定实现：以本人或本单位亲历事实为主线，保持专业克制；用户要求只说明自身问题时不强行提出解决建议；材料已给简要投诉请求时保留请求，但不替接收方设计整改方案。

## 公开规则校准

- 《信访工作条例》第十七至十九条表明，情况反映、意见建议和投诉请求是可区分的提交目的；书面事项需要载明请求、事实和理由，并对材料真实性负责。
- 市场监督管理总局现行投诉处理规则要求投诉具有具体请求和相应事实依据。由此可见，投诉请求与解决建议需要分别处理，不能因用户不要求提出方案而删除已给请求。
- 政务服务热线公开分类通常将投诉与建议分设，支持本轮用独立路由而不是复用意见建议模板。

公开材料只用于校准文种、要素和语气，不进入任何测试稿事实。

`cases.json` 包含三道正向题和两道控制题：平台投诉栏、独立情况反映、带明确核实请求的投诉、合作性意见建议控制、收到投诉办理记录控制。Baseline 与 Candidate 使用相同请求。

## 真实写稿准入门

1. 三道正向题保持给定主体、日期、次数、金额或编号、沟通经过和当前状态；允许材料直接支持的一层影响归纳，不因合理归纳判失败。
2. 用户明确不要求解决建议时，不新增平台改造、流程优化、责任分工、办理期限或结果承诺；不强制表扬，不把个人经历扩大为普遍现象，不作无依据责任定性。
3. 材料已给`请核实并反馈`等请求时必须保留；请求本身不按解决建议判失败。
4. 合作性意见建议控制仍应提出有权对象和具体建议；收到事项办理记录控制不得改成亲历方再次投诉。
5. 候选不要求文采逐项胜过基线。只有与候选规则可归因的事实、状态、主体、文种、请求或交付形态硬回退才阻断；单一 provider 风格摆动先记录并最小复核。
6. 至少两个独立 provider 实际读取新叶并呈现目标改进，五家有效正向稿总体可用，控制题没有跨 provider 候选相关硬回退，才进入镜像和工程门。

若首个候选未通过，按失败对应的单一子句继续最小调整，不用扩大裁判或堆确定性测试替代真稿改进。
