## 逐项判定

| 外部报告主张 | 复核结论与处理 |

| 自加当天落款是规则回退 | **按当前用户要求属于误判。** 候选 6/8、有效基线 1/7 的现象属实，但题目均未要求日期留空或逐字保持。用户已明确允许需要落款时补经确认的当天草稿日期；见 [Spec 日期校准](../../../specs/reference-rewrite-20260912.md)。公告草稿上的日期不等于已经执行发布。保留业务日期、正式签发依据及明确空位的区别，不恢复“必须用户另外要求完整落款”的旧限制。 |

这里展示修正方向，不覆盖原始终稿。这些问题证明仍有漏检、无依据扩写和交付版本失配；已有规则覆盖相应原则，尚未定位到值得再加一条同义命令的共性缺口。双方都出现某类错误也不等于该错误可以忽略，只是不能据此认定候选独有回退。

## 胜负与效率重新校准

不直接沿用报告的“5 胜 3 平”：两对采购公告的基线均写齐给定要素，125 字也高于既定 80 字下限；没有固定结束语、分段更少或没有跑脚本，都不足以单独判正文质量败。议案两侧分别有占位或既有草案细项扩写，不能凭候选脚本调用判胜。MiniMax 公告的基线正文外追问也不能作为主要败因。此次不另编一个总胜率。

记录的总量核对无误，但原表比较了 7 次成功基线和 8 次成功候选。仅取双方都有终稿的同 7 对，得到：

| 指标 | 1.x | 2.0 |
| --- | ---: | ---: |
| 平均调用耗时 | 60.034 秒 | 76.564 秒 |
| input tokens | 1,187,271 | 1,233,187 |
| 未缓存 input tokens | 156,722 | 116,932 |

本批同题配对下，候选未缓存输入较少，但平均耗时更长。两通道混合且样本少，未比较实际账单，不能外推普遍省钱或提速；超时那题的部分用量没有完整记录。脚本执行更充分可作为执行观察单列，不能直接计作正文质量收益。
