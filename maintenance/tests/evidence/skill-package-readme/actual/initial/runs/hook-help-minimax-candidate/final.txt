# 中文公文写作 Skill 中 Hook 的作用与启用方式

## Hook 主要做什么

Hook 是这个 Skill 的**可选"交付复核"增强**，定位是给已经完成的完整初稿（D0）再补一道有界的机器复核，本身不是起草或改稿逻辑。关键点：

- **作用对象**：完整初稿形成之后、正式交付之前的一次额外检查。
- **检查范围**：聚焦事实、状态、结构层面已暴露的风险，例如数字、主体、未决状态、办理表述等。
- **兜底原则**：检查未通过或运行异常时，**优先交付原始完整稿，不反复改写**。
- **默认行为**：候选稿通过所选能力的机械与语义核验就采纳为 D1，否则**逐字回退到 D0**。
- **可选能力（静态互斥）**：默认走既有"交付复核"，也可在组装前显式切换为：保护性外扩精确删除、篇幅不足补足、超长收束、交付洁净度、重复句整理。
- **与 prose_lint 的区别**：`scripts/prose_lint.py` 是只读的语言/格式提示；Hook负责交付复核，两者各自独立运行。
- **代价**：Hook 会增加事件处理和有限的修订核验，多数任务比普通 Skill 略慢；超长收束在首次压缩仍超限时最多再压缩一次。重要材料仍需责任人员做事实核对和正式审签。

另外 Hook 配有专用协议页 `references/delivery-review-gate.md`，**不属于普通写稿流程的默认加载资料**。

## 安装 Skill 会自动启用 Hook 吗

**不会自动启用**。Skill 入口 `SKILL.md` 和 Hook 入口 `hooks/README.md` 都已经明确：

- "下载、安装或调用普通 Skill **不会自动启用 Hook**。"
- "本目录只保存静态能力与兼容文件，**不自动识别宿主、不生成安装包、不安装插件、不修改配置，也不主动联网**。"
- `SKILL.md` 末尾："用户明确要求处理交付门禁 Hook 时，读取 `hooks/README.md`。**普通起草、改稿、压缩和复核不加载该页，也不自动启用 Hook**。"

要启用必须走人工显式确认流程：

1. 由用户**明确要求**为某个宿主启用 Hook；
2. Agent 先向用户**展示宿主、目标目录、拟复制文件和所选能力**；
3. 用户**确认后**才组装"胶水层"（manifest + 薄适配器 + canonical Skill 副本 + 门禁脚本）；
4. 先跑宿主 validator 和离线事件 smoke，**再由用户决定**是否真正安装或加载；
5. **组装完成不会自动进入安装步骤**——组装、安装、启用、宿主信任确认这几步是分开进行的。

已支持、需要单独走对应适配器流程的宿主包括：Claude Code、Codex、WorkBuddy / CodeBuddy、ZCode、Qwen Code、Kimi Code CLI、OpenCode、Hermes Agent、DeepSeek Harness 等，各自的启用校验命令（如 `claude plugin validate --strict`、`codebuddy plugin validate`、`qwen extensions list`、`hermes plugins enable` 等）都列在 `hooks/README.md` 的"宿主适配说明"表中。

## 关于"本次关闭"

如果只是想临时跳过，不需要卸载：

> 本次关闭 Hook，按普通 Skill 完成。

也可以说"本次不要用 Hook"或"跳过交付门禁"，Agent 会记 `bypass=user_requested`，不创建门禁事务、不调用门禁、不阻断终稿。已安装的 companion 仍会收到宿主事件，关掉的是当前任务的门禁。

完全关闭或永久移除包内 Hook 源文件的具体命令、目录范围和确认流程，都在 `hooks/README.md` 末尾两节，可按需取用。
