# WR-028 整改方案专项叶 R1 预登记

## 当前缺口

`main@5869234bcfee5aeb7f70762035a8ee593569fbc3` 只有 `genre-playbook-plan-construction.md` 的方案通用骨架，没有整改方案直达路由或专项叶。当前产品在情况说明、投诉、审稿等非整改任务中正确限制擅造整改方案，但没有与之对称的正向规则说明：当用户明确要求本单位制定整改方案时，未来措施是文种必要内容，合理的原因分析、影响判断和条件性预期不应被事实边界误压掉。

官方正文样本与规范性校准见 `official-corpus.md`。稳定共性是问题和措施逐项对应，并按材料和任务补足原因、目标、责任、进度及验收；篇幅和目录随任务复杂度变化。

## 固定验证口径

- 真实写稿先于镜像、单测和全量工程门。先固定当前 main 运行五家登记低成本 provider，再做最小候选同题 A/B。
- 合理扩写不是失败：材料事实与常识直接支持的一层原因、逆推原因、直接影响、整改必要性、条件性预期和职责范围内未来措施均允许。
- 原因证据不足时应校准为分析或可能性判断，不把动机、过错或未知责任人写成已核实事实。
- 方案必须出现可执行的整改措施；不要求每稿都具备领导小组、问责、销号、固定阶段、固定条数或固定字数。
- 只有与候选直接相关的事实遗漏、状态升级、错误责任关系、文种误路由、正文外包装或不可用输出才阻断。单纯文风偏好、合理结构差异和候选之外的既有问题只记观察。
- 不用正文长于提示词、指定套语或硬字符数替代质量判断。

## 真实写稿矩阵

五家均通过 Codex Desktop CLI 的隔离 Skill 目录运行，`max`，每题每模型每臂一次；技术失败不计质量，不用贵模型补普通写稿。

1. `REMEDIATION-SHORT-SERVICE`：精炼的政务服务窗口整改方案。检查能否由抽查事实形成有校准的原因判断，提出与清单版本和口头告知直接对应的措施，并保持“尚未形成统一版本、整改尚未开始”。
2. `REMEDIATION-AUDIT-MEDIUM`：中等篇幅审计整改方案。检查四类问题是否分别绑定原因、措施、给定责任角色与统一期限，不把未整改写成已完成，不虚构资金损失或责任认定。
3. `REMEDIATION-EDUCATION-LONG`：较长教育评估整改方案。检查前后结构、五类事实状态、分阶段任务、责任和验收，允许合理归因及预期影响，不把在修订或待复核写成批准、完成或达标。
4. `CONTROL-REMEDIATION-PROGRESS`：整改进展情况报告。候选不得因“整改”二字误读方案叶或把已给进展改写成新方案。
5. `CONTROL-IMPLEMENTATION-PLAN`：普通系统上线实施方案。继续使用方案通用叶，不读整改专项叶，不擅自制造“问题整改”叙事。

## 是否形成和选择候选

- 基线若在至少两家有效 provider 的正向稿共同出现措施与问题脱节、完全不分析可合理归因的原因、把预期写成既成成效，或因过度保护而只复述问题，启动专项叶候选。
- 候选产品范围限于 canonical `SKILL.md` 的整改方案直达路由与一页专项 reference；不改 description、Hook、通用事实边界或其他文种叶。
- 候选需在至少两家有效 provider、至少两个正向题上产生与目标直接相关的可复现改善；所有有效正向稿必须包含实际整改措施，且无候选独有事实、状态、责任、文种或交付形态硬回退。
- 两个控制题不得读取整改专项叶。若路由误伤，先最小修复后重跑对应原子，不用扩大评审门替代写稿修复。
- 真实 A/B 通过后，才同步普通兼容镜像、增加直接路由/边界断言并运行 quick validate；本轮未经用户另行授权不合并 main、不推送、不发布。
