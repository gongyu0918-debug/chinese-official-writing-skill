# 连续否定式收口 R3 正向示例预注册（2026-08-09）

## 触发证据

R2 的可见 Codex 内联消融使用 Alibaba Token Plan 与 Ollama Cloud DeepSeek V4 Flash 0731 `max`。T1 两家候选均删除无办理作用的三句保护性尾巴，但基线也能完成；Alibaba 基线另把“接口恢复”补强为“恢复正常”，候选没有。T2 四稿仍分别写“未就设备采购作出决定”“未形成采购决定”，说明 R2 能列出反例，却没有给出足够明确的正向承载方式。

分支读取复放因四个线程均无工具调用而无效；模型后续声称已执行 `Get-Content`，但任务记录仍只有用户和最终消息，属于不可采信的工具声明。上述内联消融只验证 Prompt 片段，不证明真实 reference 加载率。

## 唯一候选

只在现有“连续否定式收口”同一项目末尾增加一个正向示例：材料只记载会议听取情况时，用“会议仅听取相关情况”承载当前状态，不再追加采购、安排或责任未决句。

不新增第二条规则，不扩展词表，不改其他 Anti-AI 项、SKILL、脚本、路由或终稿流程。相对 R2 的规范化净增不超过 55 字符。

## 真实复放

只复放 T2，自助借还设备事实包和硬边界逐字不变。Alibaba 与 Ollama 两家 DeepSeek V4 Flash 0731 `max`，R2/R3 内联单变量；每臂首个最终冻结。R3 两家都应以“馆务会仅听取试用情况”或等价正向事实承载未作采购决定含义，并不再追加“尚未/未形成/未作出……决定、责任分工未确定”。

任一 R3 写成已采购、已决定、拟采购、安排采购，或新增预算、责任、评估、整改、后续动作，立即失败。只有一家的措辞变化或两家都继续追加否定决定句，记 `NO EVIDENCE`，不再增加更多示例。
