关于版慎通智能审校系统新增"公文 AI 写作"功能的立项申请

公司领导：

为补齐版慎通智能审校系统在写稿环节的能力短板，把握已在外部开源生态完成市场验证的成熟方案进入公司产品线的窗口期，经项目团队研究，拟立项开展"公文 AI 写作"功能模块的研发与集成。现就立项依据、目标、建设内容、技术路径、模型工具费用及申请事项请示如下。

一、立项缘由与必要性

（一）现有系统能力存在明显缺口。版慎通智能审校系统目前已具备较为完善的图书审校能力，覆盖文字差错、体例规范、知识核对等审校环节，但全流程止步于审校，不具备写稿能力。在机关、企事业单位的日常办公场景中，审校与写稿常常前后衔接，单一审校工具无法支撑用户从起草到定稿的完整需求，导致用户只能在审校系统和外部写稿工具之间频繁切换，跨工具带来的格式损耗、口径不一致和返工成本较高。用户长期呼吁在审校系统内一并提供写稿能力。

（二）写稿需求具有普遍性和市场容量。机关公文、企事业事务性材料、新闻通稿、规章制度等正式文本的写作是各行业基础办公需求，覆盖范围广、复用频次高，对专业化 AI 写作能力有持续且旺盛的需求。立项新增写稿功能，可将版慎通的使用场景由审校环节延伸至起草环节，直接扩大用户群体，提升单位时间内的用户活跃度和续费意愿。

（三）同类需求已在外部生态完成规模化验证。本项目相关能力已通过开源 Skill 形态在公网发布并长期运行，截至当前在 skillhub 累计下载约 10.5 万次，位列平台下载榜前 50，公文写作领域排名第一；在 clawhub 累计下载约 7000 次，趋势榜长期保持前 100，公文写作领域排名第一。其变体作品"公文写作智能体"获江西出版集团首届 AI 大赛专业组第三名。累计 10 万级以上的下载量足以证明专业 AI 公文写作能力存在稳定、可持续的市场需求。

（四）已出现明显的外部复用迹象，存在能力窗口收窄风险。经对市场上同类产品做指纹比对，包括深知、WPS 在内的多家公司的公文写作产品中均存在复用本项目代码的痕迹，尤其集中在去 AI 味模块、短稿路由模块和检测脚本模块。外部复用一方面反向印证了本项目技术路线的市场价值，另一方面也提示相关能力正成为行业基线配置，版慎通如不尽快集成自有写稿能力，将面临产品差异化收窄、用户被分流的风险。

二、立项目标

本项目拟在版慎通智能审校系统现有架构上，新增"公文 AI 写作"功能模块，重点提供四项能力：

（一）AI 智能写作。基于用户输入的事项、对象、依据和用途，生成符合公文体例与行文规范的初稿，覆盖通知、报告、请示、函、纪要、方案、制度、总结、讲话稿等常见文种。

（二）红头文件生成。支持版头、发文字号、主送机关、正文、附件说明、落款、成文日期、版记等要素的模板化生成与排版校验，输出符合 GB/T 9704—2012 要求的版式。

（三）格式修复。对用户导入的草稿进行体例、序号、字体、段落、引用、附件等格式项的自动校正，使成稿与公文规范对齐。

（四）AI 味审校。在文种合规与体例合规的基础上，进一步识别模板腔、口语化、机械排比、模糊归因等 AI 生成特征，辅助成稿回归平实、克制的正式表达。

项目落地后，版慎通将形成"审校 + 写稿"完整闭环，用户可在同一系统内完成起草、规范校验、AI 味审校和最终交付，提升产品竞争力与垂直市场覆盖。

三、建设方案与技术路径

（一）形态选择。项目对外开源版本采用 Skill 形态，已在多类 AI 编程与写作环境中适配运行；公司内部版本需进行闭源改造并完成与版慎通现有审校模块的深度集成。结合市场行情、版慎通现有架构及上线节奏，Skill 形态较完整 Workflow Agent 形态更易复用既有规则资产、迭代效率和适配成本更优，本项目确定以 Skill 形态作为公司内部产品实现路径，对外开源版本与公司闭源版本分别维护。

（二）三大模块技术架构。改造后的产品按 references、hooks、scripts 三大模块组织：

1. references 模块。承载公文与事务性材料的专用写作路由。规则源自真实写稿实践与公开成熟公文范本，按"从大到小、从粗到细"逐级收敛，覆盖文种判断、行文关系、办理要素、论证链条、语言风格、格式版式等维度，形成一套成熟且复杂的公文写作规则路由系统。模块采用按需热加载方式，平均每次写稿热加载规则稳定控制在约 14K Token，显著低于同类 Skill 约 100K Token 的平均水平，可在保证专业性的同时有效节约推理成本。

2. hooks 模块。承担成稿阶段的微调与校验。围绕两个生命周期展开校验：一是"提纲—正文"一致性，重点核对写作提纲与正文落实情况的吻合；二是"成稿—交付"合规性，重点核对对外交付稿件的最终质量。校验维度包括字数一致性、提纲与正文一致性、篇幅一致性、AI 味词汇检测、Prompt 遵循度等。对 Agent 在校验中识别出的问题，模块返回模型进行定向修改；在三轮 ReAct 迭代范围内，最终成稿错误率可控制在约 1% 左右。

3. scripts 模块。承担显式 AI 味清洗、Markdown 残留处理与格式校验。在 hooks 完成语义层校验的基础上，对残留的 Markdown 标记、口语化表达、模板腔句式进行显式清洗，并对最终交付稿件的格式、标点、版式要素进行校验，确保交付件可直接进入办公流程。

（三）与版慎通的集成方式。references 提供写稿主能力，hooks 提供成稿校验，scripts 提供交付前清洗与版式核对；与版慎通现有审校模块按"写稿 → 校验 → 审校 → 交付"流水线串联，用户在审校工作流中可直接发起写稿任务，并在审校环节复用同一份规则路由与检测能力，避免规则双轨、维护成本上升。

（四）闭源与适配。本项目将原 Skill 中涉及核心规则路由、提纲—正文一致性算法与 AI 味检测的关键代码转为公司内部闭源资产，按公司研发管理与代码保密要求进行版本控制、权限分级与代码审计；同时按版慎通现有接口、用户体系、计费体系和数据合规要求完成适配，确保上线后与既有审校模块在体验、权限和数据流上保持一致。

（五）开发流程与项目 LOOP。本项目延续原 Skill 已验证的迭代流程，采用"idea → 登记为 OpenSpec 需求 → 独立 worktree 预先修改 → 真实写稿 A/B 测试 → 通过后补工程与胶水 → 并入 main"的标准开发回路；如未通过测试，则总结经验并开启新的 worktree 进行下一轮尝试。该流程已在原 Skill 长期运行中验证对写稿类项目具备较好的可控性与可回滚性。

四、模型开发工具与 Token 费用测算

（一）当前与近期主力开发工具。本项目由个人项目转为公司项目，开发工具与模型选型需按公司项目要求重新配置。开发主力采用 Codex，开发流程涉及主力开发与真实写稿测试两类用途，单日 Token 消耗约 10 亿，其中主力开发模型消耗约 7 亿、测试模型消耗约 3 亿。

（二）费用测算。综合开发强度与上文日均 Token 消耗水平，前几个月拟按每月 1600 元标准订阅 Codex Pro 20X 作为主力开发工具，并辅以适量 Alibaba Token Plan 用于 Qwen 系列模型的适配与对照测试，确保主力模型与适配模型在写稿场景下均经过充分验证；后续视开发进度、用户增长与功能成熟度，可将主力开发工具切换为每月 900 元的 Codex Pro 5X，以压缩工具成本。

（三）费用性质。模型开发费用属于项目研发投入，与功能上线后的运行算力、用户调用算力分属不同口径，不在本次立项申请范围内；上线后的运行算力及对应采购或租赁方案，由项目团队另行评估后按公司采购程序办理。

五、申请事项

综合上述立项缘由、目标、建设方案、技术路径与开发工具费用，恳请公司批准本项目立项，并就以下事项予以支持：

（一）批准"公文 AI 写作"功能模块立项，纳入版慎通智能审校系统下一阶段产品规划；

（二）批准按本申请所述 Skill 形态作为公司内部产品实现路径，同意对原开源 Skill 进行闭源改造并完成版慎通适配；

（三）批准前几个月按每月 1600 元标准配置 Codex Pro 20X 作为主力开发工具，并配置适量 Alibaba Token Plan 用于 Qwen 模型适配；后续视情况切换为每月 900 元的 Codex Pro 5X。
