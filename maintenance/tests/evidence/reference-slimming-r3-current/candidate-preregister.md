# REVIEW-DIRECT-LEAF-R1 预登记

## 原子

只调整“点名范围、只审不改”的 reference 路由：新增一个轻量定向审稿执行页，保留原 `review-checklist.md` 作为段落、小节、全文、格式、语气或综合审稿入口。不得同时修改 description、短稿规则、Hook、版本、包体或其他文种内容。

## 假设

当前基线在请示、报告、通知只审任务中分别有 3/5、4/5、5/5 读取 16,510 字节的综合审稿页。专项文种叶和入口硬边界已经覆盖主要审稿目标；小型定向页可减少无关层级、联网、Word、AI 算力、长稿压缩等检查项伴读，并减少由伴读诱发的过严建议。

## 同题 A/B

- 正向：`REVIEW-REQUEST-ONLY`、`REVIEW-REPORT-ONLY`、`REVIEW-NOTICE-CONTROL`。
- 直达对照：`REVIEW-FEASIBILITY-ONLY`，不得因新叶反而加载综合页。
- Provider：Alibaba Token Plan 2、Alibaba Token Plan、Ollama Cloud DeepSeek V4 Flash 0731、OpenCode Go DeepSeek V4 Flash、MiniMax M3；推理强度 `max`。

## 通过条件

1. 至少两个正向任务各有 3/5 有效 provider 读取新轻叶，且 `review-checklist.md` 读取相对基线下降；每条命中新叶的记录应有可计算的 reference 省读。
2. 所有有效候选稿保持只审不改及“位置、风险层级、修改建议”形状，不打分、不交改后全文。
3. 请示保留 2 台、2.4 万元、4.8 万元、供应商尚未确定，并识别知悉/请批功能和结尾语位置；报告保留 34/31/3、原因未查明、时间未定，并清除旧数据与旧承诺；通知保留办公室、各窗口、业务协调处、OA、完整 17 时、落款和日期；可研保持三项点名范围和未决结论。
4. 不因新路由新增供应商、采购方式、审批结果、责任部门、调查程序、联系人、处罚、委托关系、反馈材料形式或完成承诺。
5. 基于给定事实和常识的一层原因、作用、透明算术、条件性结论，以及指出材料已有要素的合理完整性建议，均不算失败。
6. 只把候选 diff 可归因的事实、状态、文种、输出形状或直接可用性硬回退计为失败。模型随机风格差异、自动字面误报和基线已有问题不单独否决候选。

## 终止条件

- 基线读取大页的目标未转读轻叶，或省读不稳定。
- 新叶导致已给事实遗漏、未决状态升级、请示/报告/通知功能错位、只审不改失效或材料外具体建议增加。
- 为救候选需要增加第二个产品原子、修改 description 或堆叠强制入口提示。

## 工程门

真实 A/B 通过后，才运行 reference 链接、Skill 路由、quick validate、包体与状态一致性测试；真实 A/B 未通过时只记录结果并恢复产品。
