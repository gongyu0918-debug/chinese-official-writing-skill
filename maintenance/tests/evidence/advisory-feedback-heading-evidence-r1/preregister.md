## 用户观察与拟提升的共性

真实算力补贴申报建议稿暴露出两项相互关联的问题：

1. 对外、合作性提出建议时，建议分项标题如果只写成“完善审核机制”“优化平台功能”，容易被读成被建议方的内部部署事项；标题优先采用“建议 + 动作/对象”，能同时标明文种行为和权限关系。
2. 申报建议的依据应以建议方亲历的申报、办理、使用或服务事实为主。其他地区、单位或平台的公开做法只用于补充说明可行路径，不能取代本地问题证据，更不能被改写成收文方已有制度、既定部署或必须照搬的方案。

该规则拟提升到上轮 `WR-025` 专叶，覆盖意见建议、建议反馈和反馈意见；不扩展到正式下行指导、内部整改部署、监督检查、安全整改、审计或纪检建议，也不要求反馈办理结果的每个标题机械加“建议”。现有 `WR-025b` 已登记“共性问题与建议归并”，本原子编号为 `WR-025c-EXTERNAL-ADVICE-HEADING-EVIDENCE-R1`。

## 真实写稿题与反向控制

五家仓库登记的低成本写稿路线均以 `max` 思考强度运行：Alibaba Token Plan 2、Alibaba Token Plan、Ollama Cloud DeepSeek V4 Flash 0731、OpenCode Go DeepSeek V4 Flash、MiniMax M3。

正向题：

1. `ADVICE-SUBSIDY-EXTERNAL-EVIDENCE`：企业向补贴主管、审核部门和平台运营方反馈两次真实申报经历，并附一项外地公开做法；观察分项标题、第一方证据优先级、外部做法边界和处置权。
2. `FEEDBACK-TRAINING-GRANT-EXTERNAL-EVIDENCE`：行业协会汇总会员申报培训补贴的实际材料差异，外省问答只作辅助；观察规则能否跨出算力场景。
3. `FEEDBACK-MULTI-AUTHORITY-HEADING`：同一反馈同时涉及审核口径与平台上传功能，均未形成调整决定；观察建议标题和有权主体能否共同保留。

反向控制题：

4. `CONTROL-INTERNAL-PLATFORM-DEPLOYMENT`：平台运营方给内部技术团队下达已批准的改造任务，不应把部署标题统一弱化为“建议”。
5. `CONTROL-AUDIT-RECTIFICATION`：监督检查已确认问题并要求限期整改，不应套用合作性建议标题或商请语气。

## 判据

只评价与本原子直接相关的差异：

- 正向题的建议分项若使用并列小标题，优先出现“建议 + 动作/对象”；不强制正文每句重复“建议”。无建议小标题、但结构本身不是分项标题体时，不仅凭缺词判失败。
- 第一方实际申报、办理、使用或服务事实应先构成问题判断和建议依据；外地做法只能作补充比较，须保持给定来源、未核实或适用待研究状态。
- 不得把外部做法写成本地现行规则，不得把建议方写成已经决定平台上线、审核认可、材料豁免或制度调整；具体动作应绑定有权对象。
- 控制题不得候选独有地把已批准内部任务或限期整改弱化为建议、供参考或可酌情处理。
- 仍按既有规则保留数字、日期、状态、主体和直接可用正文。基于给定事实、常识和二者直接支持的一层归因、总结、作用或条件性结论不是失败。
- 只有跨 provider 的可归因改善才进入工程门。单模型随机文采、篇幅、未读取专叶、技术失败和与本 diff 无关的旧问题不冒充候选回退。
