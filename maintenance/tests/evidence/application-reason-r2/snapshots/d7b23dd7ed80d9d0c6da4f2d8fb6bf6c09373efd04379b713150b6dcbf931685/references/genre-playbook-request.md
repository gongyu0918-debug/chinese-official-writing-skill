# 请示/申请 Playbook

本文件用于请示、申请命中常规或完整骨架时直接进入对应文种规则。

## 使用方式

- 路由已确定为请示或申请后进入本文件；工作流、事实选择和文种冲突按已命中的共性页处理。
- 用户已有模板、称呼、字段顺序和落款方式优先；本文件只确定文种骨架和风险点。
- 事实、状态和缺项统一按 `information-selection.md` 处理。

## 请示/申请

请示用于请求上级指示或批准，一文一事并落到请批事项；申请保留原因、依据与申请事项。主送采用用户给出的接收对象，机关名、部门名或职务称谓均按材料使用；落款采用已给的发文或申请主体，具体位置服从用户模板。

- 适用：向上级、领导班子或审批方请求批准经费、事项、资源、立项、采购方式。
- 骨架：请示通常按请示缘由、请示事项、请示要求组织。申请写清原因、依据或必要性，让读者理解因何产生本次需求，再承接具体申请事项、方案或金额、当前状态和请批语。短稿可合并句段，缘由到请求的关系仍要完整。
- 风险：请示一文一事；申请保留用户模板和称呼，文种根据用途判断。“妥否，请批示”可用于相应的申请。未给的主送、申请单位和日期按 `information-selection.md` 核对缺项，正式成稿清理无用途的占位。
- 形成理由：把材料中的现状、使用需要或制度依据组织成申请缘由，主动写出事实和常识直接支持的一般必要性、目的或用途。说明“因何需要更新、补足或配置”，再接“为此申请什么”；只并列现状和数量，或换述“为了购买而申请购买”，都还没有完成理由。完全缺少用途和依据时，将真正影响成立的原因缺口按 `information-selection.md` 处理。
- 采购申请依次说清缘由与使用需要、拟购品名规格和数量金额、请批事项。根据实际内容展开句段，用户要求简短时可合为一至两个自然段。现有资源数量、使用负荷、排队共用、已确认损坏等事实可支持对应的使用需求；具体故障、损失、政策条款、采购程序或审批结论仍以材料为准。多品类、分项核算、比价验收、技术附件或明确长篇任务仍以本页为主文种；需要核对主体、金额、期限、附件或反馈时加读 `handling-elements.md`，需要解释必要性或比较方案时加读 `argument-chains.md`；字段表格保持原结构。
- 请假申请一般写明假别、事由或制度依据、起止时间和已给交接安排。年休假、婚假、产假等依规申请的假别，可在申请事项前使用“根据有关休假规定”等不特指条款的一般依据，不强行编造个人私事原因；事假、病假等完全未给具体事由时，不用“因个人事务”“因身体原因”等泛称代填。材料只给工作交接时，不据此补“工作不受影响”、通讯承诺或代办责任。
- 材料只写设备老旧时，可据此说明更新设备、满足已知场景基本使用需要的目的；运行缓慢、无法使用、影响服务或已经造成损失等更强事实需要材料支持。采购进展、供应商和后续安排沿用材料给出的状态，供应商未定仅说明当前未定。篇幅调整保留完整理由、申请事项和请批动作；材料不足以继续展开时按 `information-selection.md` 处理。
- 需要论证或称谓复核时，结合 `argument-chains.md` 核对依据与请求之间的关系和 `formal-addressing.md`。
