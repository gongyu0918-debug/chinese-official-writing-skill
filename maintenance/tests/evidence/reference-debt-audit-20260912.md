# Reference 工程债与旁白压制审计（2026-09-12）

## 当前判断

旁白规则不是完全缺失，而是分散在入口、workflow、总审、反 AI、校对清单、review checklist、prose lint 和可选 Hook 中。相同的“正文不得出现读取/复核/制作过程”语义重复出现，部分旧叶又同时承担文种骨架、办理要素、技术审查和质量建议，容易让模型把处理过程当成正文任务的一部分。

现有 `prose_lint.py` 对“已按 Skill 读取……正文如下”“本轮按任务要求复核完成，稿件如下”等变体曾漏检；本候选只增加两组高风险 `delivery-explanation` 检测，不自动删除正文。

## 已确认的债务簇

- `ai-compute-docs.md` 同时覆盖可研、采购/租赁方案、技术需求、SLA、安全和验收，约 8.3 KB；不宜直接整页拆空，需先做当前基线读取追踪。
- `review-checklist.md`、`final-review-layers.md`、`anti-ai-patterns.md`、`workflow.md` 和 `review-checklist.md` 之间存在交付洁净、过程泄露、按需读取和最终复核的重复语义。重复规则总量大于单一入口硬边界，可能造成注意力稀释。
- 文种 playbook 旧叶仍有混合承载。`genre-playbooks.md` 已完成一轮族群拆分，但历史的通知、纪要、采购公告和复核层拆分实验曾出现基线不读大页、候选读错控制叶、对象扩大或材料外安排，不能据静态字节直接继续拆。
- 既有 `ANTI-AI-SINGLE-SURFACE-ROUTE` 基线只在 15 次中 1 次读取完整反 AI 页，说明“先拆过程旁白子叶”缺乏稳定路由前提。

## 旁白脚本候选的真实验证

`delivery-preface-lint-r5` 使用当前五条客户端通道、同一通知题、同一 `max` 和同一脚本调用要求。候选 5/5 输出为正文；基线 4/5 为正文，MiniMax 首轮只输出“我先读取指定的 Skill 文件以了解要求”。同一基线提交的 MiniMax 精确复跑随后输出完整正文，说明该单点主要是模型采样波动，不能把 5/5 对 4/5 记成脚本稳定收益。

候选五臂均实际执行 `prose_lint.py --delivery-mode draft-body --strict --fail-on high`；脚本检测到了新增旁白模式时返回高风险，未检测到时返回 0。该机制能提高发现率，但只有宿主或模型实际调用脚本并按非零结果重试，才会转化为交付压制；当前普通 Skill 路径仍不自动调用脚本。

因此本候选暂不合入 `main`：没有候选质量回退，但也没有足够证据证明新增检测本身让旁白率稳定下降。可选 Hook 的 `delivery_cleanliness` 已有删除、语义核验和 D0 回退闭环，后续应优先验证其在真实宿主中的旁白命中率，再决定是否改变普通路径。

## 后续安全顺序

1. 保留入口中的一条短硬边界，把重复的过程泄露说明改为指针，不先删除各叶中的事实和状态保护。
2. 对旧混合叶先做五路当前模型基线 trace，确认确实被共同读取后再立一个单一拆分原子；基线未读或控制串叶即终止。
3. 对 `prose_lint` 新检测做同题多 provider 复跑，分别统计旁白发现、重试后正文洁净、事实/状态保持和误报，不用单次干净稿宣称稳定改善。
4. 任何路由减载都必须把“少读目标叶”和“正文不劣”分开验收；静态字符减少不等于实际 token 或总读取成本下降。

本审计只提交证据和窄脚本候选，未修改 `main`、版本、Hook 默认选择或发布面。
