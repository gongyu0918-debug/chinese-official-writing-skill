# References 减载 R2 预登记

## 目标与边界

本轮只研究运行时实际读取减载，不以文件体积、规则字数或模型偏好替代真实收益。固定基线为 `v1.6.20` 发布回执后的 `main@6e4e8914431c5674a3fda87ab42d35ed8a531e8c`。先让五条登记低成本路线各完成六个真实起草、改稿或技术审查任务，再依据 CLI trace 判断大页是否真的被读取；未形成稳定基线读取的候选不做产品原型。

本轮不修改 description、Hook、adapter、发行包和付费提纲分支，不重跑已经终态拒绝的 `MINUTES-CHECKLIST-LEAF-R1`、`NOTICE-LEAF-CURRENT-R1`、`PROCUREMENT-ANNOUNCEMENT-LEAF-R1/R2`、`REVIEW-LAYER-SPLIT-R1`，也不复活常用语机械化旧方向。

## 三个原子

### `FINAL-BODY-LEAF-R1`

- 假设：普通起草会实际读取 8961 字节的 `final-review-layers.md`，但只需要正文交付前的硬边界、标题层级、事实状态、正文包装和基础格式复核；多轮改稿、多人合稿和完整审稿才需要完整页。
- 基线题：稀疏采购申请、完整日期活动新闻、普通长报告。
- 能力控制：多材料合稿、算力可研。
- 只有至少 3/5 provider 在至少两个普通起草题真实读取该页，才允许做轻量正文总审叶原型。

### `WORKFLOW-REVISION-LEAF-R1`

- 假设：普通长报告会实际读取 15443 字节的 `workflow.md`，其中“多轮修改和结构指令—素材映射—网页稿和套嵌文件边界”只需由复杂改稿、多材料合稿、结构锁定或网页稿任务加载。
- 基线题：普通长报告。
- 能力控制：多材料合稿；其他短稿不应为本原子强制加载工作流。
- 只有普通长报告至少 3/5 provider 读取完整工作流，才允许把上述连续区段拆成一张条件叶；完整工作流任务允许读取核心页和条件叶两张。

### `AI-COMPUTE-BASIC-LEAF-R1`

- 假设：简单算力服务采购申请会实际读取 10568 字节的 `ai-compute-docs.md`，但无需完整成本路径、技术指标、SLA、安全和验收审查；完整可研仍需要全部内容。
- 基线题：简单算力服务采购申请。
- 能力控制：完整算力服务可研、普通办公设备采购申请。
- 只有简单算力申请至少 3/5 provider 读取专项大页，才允许拆出基础起草叶；完整可研必须继续覆盖成本、技术、SLA、安全、状态和结论边界。

## 模型与执行

五条路线均通过 Codex CLI / OpenCodex catalog，`reasoning=max`，每个 provider、每题只取首个技术有效终稿，不因文采不合预期补抽：

- `alibaba-token-plan-2/deepseek-v4-flash-0731`
- `alibaba-token-plan/deepseek-v4-flash-0731`
- `ollama-cloud/deepseek-v4-flash:0731`
- `opencode-go/deepseek-v4-flash`
- `minimax-cn/MiniMax-M3`

运行时只安装固定提交导出的 canonical Skill，显式禁用用户目录同名 Skill。每次调用保存终稿、JSONL trace、stderr、usage、实际读取文件和读取字节。技术失败最多允许同 provider 同题一次定向重试；重试只补技术样本，不改变首个有效稿。

## 质量裁决

先看终稿是否可直接使用，再看候选是否减载。以下属于硬回退：

- 丢失材料明确的主体、对象、数字、完整日期、范围、状态或文种功能；
- 新增具体型号、金额、供应商、程序、责任主体、期限、既成决定或既成效果；
- 把局部完成扩大为全体成效，把未决写成已决，或把选项写成已安排；
- 用户要求只交正文却输出过程说明、自评、字数、Markdown 包装或未完成占位；
- 长稿后半篇塌缩、关键论证链缺失，或多材料任务回流旧事实。

材料事实、常识以及二者直接支持的一层原因、目的、即时作用、低强度预期、条件结论和必要论证不算外扩；不能仅因正文出现这些关系判失败。篇幅没有统一下限，只有遗漏必要关系、文种功能或事项落点时才判过薄。候选间随机措辞、标题选择和非目标文采差异不计为 DIFF 失败。

## 准入和收口

1. 基线读取未达到各原子的最低门：记 `REJECTED_BASELINE_ROUTE_NOT_REPRODUCED`，不做产品修改。
2. 达门后只做一个物理拆分和对应入口路由，不同时改规则内容。
3. 候选至少要在 3/5 provider 形成目标任务真实负字节差，控制任务不串叶，并且没有候选独有硬回退，才可形成可合并候选。
4. 首个候选出现可归因硬回退时，先判断能否通过一次更小路由修复；若机制本身失败，恢复产品并进入 `REJECTED` 或 `TERMINATED`，不留下 `HOLD`。
5. 本轮没有合并、推送或发布授权；即使通过，也只提交到独立候选分支等待决定。
