## 预登记假设

- “短”只描述篇幅或交付槽位，不决定文种。平台“建议内容”栏、邮件正文等渠道已经由字段承载标题、建议人和联系方式时，可直接交付紧凑正文，不机械补完整公文壳层。
- 独立成文的正式意见建议即使篇幅紧凑，也不能仅因“短”而自动删掉任务明确要求的标题、建议方和日期。
- 问题事实、理由或依据、具体建议、对象权限和未决状态属于意见建议的文种语义，不因短而消失；普通短通知不得被改成建议口吻。
- 初始工程判断倾向意见建议专叶，但不把判断当结果；只有真实写稿、实际读取和控制题共同支持时才选择位置。

## 真实写稿范围

五家仓库登记的低成本路线均使用 `max` 思考强度：Alibaba Token Plan 2、Alibaba Token Plan、Ollama Cloud DeepSeek V4 Flash 0731、OpenCode Go DeepSeek V4 Flash、MiniMax M3。

正向题：

1. `SHORT-ADVICE-PORTAL-BODY`：政务平台单独提供标题、建议人和联系方式字段，只需“建议内容”栏正文。
2. `SHORT-ADVICE-EMAIL-BODY`：邮件客户端承载主题、收件人和签名，只需面向经办部门的简短反馈正文。
3. `SHORT-ADVICE-STANDALONE`：篇幅紧凑但明确要求独立成文，材料给出建议方和日期，观察是否误删完整稿件形态。

控制题：

4. `CONTROL-SHORT-NOTICE`：简短内部通知，须保持已决定事项和通知语气，不得因候选出现建议状态。
5. `CONTROL-FORMAL-ADVICE`：不作短稿的完整正式意见建议，观察候选是否错误剥离标题、层级或给定建议方与日期。

## 判据

- 平台栏和邮件正文题：仅交付正文，不重复标题、称谓、落款、日期或说明；仍须写清材料给出的实际问题、建议动作、有权对象和未决状态。
- 独立成文题：保留任务明确要求且材料给出的完整稿件形态；不得生成占位符、当前日期或材料外身份。
- 控制题不得候选独有地改变文种、责任强度、已决定/未决定状态、主体、数字或日期。
- 基于给定事实和常识直接支持的一层作用、归因、总结或条件性结论不判失败；只有材料外具体数字、用途、程序、承诺、责任或状态升级才是硬回退。
- 自动字面量只用于定位，不替代人工判读。单模型随机文采、技术失败、未读取目标叶和与产品 diff 无关的既有风险不冒充候选失败。
- 选择位置至少需要两家有效 provider 出现可归因改善，并且没有跨 provider 的目标相关硬回退。若两臂结果相同，优先职责归属更准确、对其他文种加载更少的一臂；若都无增益，保持基线。
