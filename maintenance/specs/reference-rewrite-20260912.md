## 2. 新架构

采用两条轴：

1. **任务轴**：起草、整体改写、局部修改、压缩、审核及审后改稿、格式交付。
2. **文种/场景轴**：请示、申请、报告、通知、函、纪要、讲话、方案、可研、采购、制度、新闻、新闻评论和兼容场景。

从用户需求确定任务、稿件用途、材料范围和交付形式，为每份独立稿件选择主叶。所有稿件共用精简的写作、复核与交付流程；专项能力依据实际任务加读。共性规则和文种规则都保留，每条规则只有一个正文归属。

页面分四层：

- **最小入口**：`SKILL.md` 承载适用范围、用户需求识别、文种选择和必要转读；具体写作、复核与交付动作归入相应规则。
- **路由入口**：`reference-index.md` 选择主文种，`genre-routing.md` 处理名称、模板、用途或关系冲突；不设置轻量任务卡或长短稿分流。
- **能力与文种叶**：共性能力各自唯一归属，文种叶各自承担文种功能、结构和状态边界。
- **执行工具**：普通篇幅和文稿复核脚本按写作阶段提供可观测检查；Hook 的宿主门禁留在 Pro，MIT 写稿链独立成立。

## 3. 规则重写原则

- 先读懂旧 `SKILL.md` 和全部 reference，再建立“旧规则→新模块”的语义映射；每条可执行语义必须保留、迁移或有明确废弃理由。
- 文种叶写本身的功能和结构；事实选择、办理要素、论证、修改、压缩、反旁白、校对和格式各有唯一共性归属，相邻动作可合并到同一页。
- 混杂旧叶改为“一个短分流页 + 必要数量的稳定主叶”。一个叶子混有两三套骨架时拆职责；职责本来单一且已有实证的新叶直接复用。
- 跨文种的固定用语、引叙、承启、敬辞和历史模板保留一个能力页；文种叶只保留本身不可缺的功能性收束和语气。只有同一规则在不同文种确实产生不同动作时才在文种叶写差异，避免复制同一用语表。
- 控制叶子数量和路由复杂度：只有在触发条件稳定、读取集合可观测、正文收益可验证时才新增叶；避免为了字符数把规则切成许多互相跳转的小页。
- 路由明确所需页面及读取条件，已经完成的动作直接进入下一步；实际读取范围、重复读取和循环由维护证据核查，不为每个叶子增加停止点或相邻禁读表。
- 组合优先采用“一个主文种首叶 + 零个或少量有证据的能力/场景叠加页”；不为同一场景制造主文种×算力×复核的叶子交叉积，也不把没有旧规则来源的个例另造页面。
- 规则优先使用正向动作：写什么、保留什么、按什么顺序、何时转读。只有安全边界无法正向表达时才用“不得/不补”等限制，并避免连续否定堆叠。
- 保留新旧文种的质量衔接：旧文种叶中已验证的事实状态、称谓、主体关系和交付形态不能因重写变弱；新叶不应被旧总页再次污染。
- 过程旁白、正文外制作说明、Markdown 包装、教学式解释和用户未要求的自证属于交付风险，应在规则和脚本结果解释中明确压制，但不把脚本提示机械升级为文种硬门。

候选与当前 main 使用相同提示、相同模型通道和相同输出要求，按单叶、二叶组合、跨文种、篇幅检查、文稿复核和正文/文后提示隔离分组测试。至少覆盖：

- 方案、研究/可研、采购审查、算力可研、算力采购/租赁、算力技术需求；

- 过程旁白、空行、Markdown 残留、状态升级、主体关系、日期和数字保真；
- 默认文后提示、明确省略提示、完整稿件自然表述、多轮未解决项接续、已解决项移除、已发现未处理错误及文件交付隔离。

每稿记录：实际读取页、首叶和停止点、正文事实/数字/日期/主体/状态、文种功能、输出形态、旁白与格式、脚本调用和技术结果。

全量构造验收还必须有一份逐页语义映射：50 个基线 reference 均标为“迁移到新页”“按证据保留”或“有理由废弃”，每个旧页面的结构、事实边界、文种功能、普通脚本契约和已验证特例都要有对应证据；Hook 页面单列为 Pro 迁移资产，不能混记为语义删除。未改页面只能凭保留理由和路由实写验证标记为通过，不能因字节未变自动通过。

排除因素：

- 两臂共有的质量问题、无损措辞变化与模型/环境波动分别记录；通道延迟和工具失败依据执行证据判断，共有问题并不等于已证明随机性；
- 只在候选出现且能归因于新规则或新路由的事实、状态、文种、格式或必要内容损失，才记候选回退；
- 门禁过严导致的失败与正文质量分开记录，不以单次门禁失败直接否定路由；
- 脚本未调用或未完成记录实际影响；偶发执行缺口按本页最新容差处理，不自动阻断或补同义规则。正文与文后提示另看实际质量，不用调用次数冒充收益。

## 7. 合并标准

只有同时满足以下条件才允许合并：

1. 旧规则语义均已归位或有明确保留/废弃记录；
2. `SKILL.md`、references、普通脚本与镜像通过静态工程门；Hook 保存分支可追溯，MIT 产品和活动构建链移除 Hook，普通脚本分工与执行顺序有效；
3. 真实写稿不存在可归因于新规则或路由的实质功能损失或反复质量退化；偶发漏读与不稳定按上述容差判断，影响使用的遗留问题应有具体文后提示；
4. 目标任务的无关 reference 伴读确实减少，主叶选择和必要组合在常见使用中稳定；偶发无害伴读单独记录，不要求每次读页集合完全相同；
5. 新旧文种质量衔接不劣于当前 main；
6. 旁白、空行、措辞变化按归因结果判断，不能把正常模型波动当作规则回退；
7. 开发改动及证据提交独立分支；上述条件成立后才具备合并资格。当前 2.0 未获合 main、安装、推送或发布授权，完成验证不自动扩大操作范围。

“完整 Skill”门槛高于静态测试通过：逐页语义映射、必要组合、五条便宜模型通道的真实写稿、实质回退归因、脚本能力和交付质量均需有对应证据。既有证据可按实际改动范围承接；间接或局部证据不能冒称全量验证，但偶发且可接受的执行波动不要求反复补测到零，也不自动阻止收口。

每个重写批次必须记录目的、涉及页面、保留语义、删除/迁移语义、静态测试、真实写稿结果、已知风险和下一批边界。产品版本和平台发布另按用户明确授权执行。
