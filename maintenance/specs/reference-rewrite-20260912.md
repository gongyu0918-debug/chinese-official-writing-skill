# SKILL/reference 全量重写 Spec

- **Spec ID**：REF-REWRITE-20260912
- **基线**：当前 `main@1ce7112303172478faa2392667a2de1098eb912c`
- **工作分支**：`codex/reference-rewrite-20260912`
- **目标**：在不降低当前 main 真实写作质量的前提下，从零重建中文公文 Skill 的规则组织，减少 reference 无关伴读、消除历史混杂、提高路由稳定性和正文执行力。

## 1. 重写范围

必须整体对照重写：

- `chinese-official-writing/SKILL.md`；
- `chinese-official-writing/references/` 全部叶子；
- `chinese-official-writing/scripts/` 的调用契约、参数说明、结果回流和必要的可复用代码；
- 与上述内容直接相关的镜像、静态测试和真实写稿测试。

不重写：

- `chinese-official-writing/hooks/` 及其宿主适配、Hook 配置、停止门和运行时能力；Hook 目录冻结，不在本轮重写。
- Hook 只作为冻结的既有资产参与回归；普通写稿不因 Hook 存在而加载 Hook。

允许复用：

- 已验证新叶的事实规则和文种骨架；
- 现有脚本的可靠实现、命令、参数和返回值；
- 现有测试夹具、模型绑定和证据格式；
- 现有 Hook 的调用接口，但不把 Hook 规则写回 Skill 主线。

“重写”表示重新划分职责、路由和组合方式，不表示把规则拆成越多越好，也不表示保留旧页面文字。

## 2. 新架构

采用两条轴：

1. **交付模式轴**：起草、整体改写、局部修改、压缩、只审不改、综合复核、格式交付。
2. **文种/场景轴**：请示、申请、报告、通知、函、纪要、讲话、方案、可研、采购、制度、新闻、新闻评论和兼容场景。

每项任务先确定交付模式，再确定主文种或场景，读取一个唯一首叶，按明确条件叠加共性叶，命中停止点后停止。共性规则和文种规则都保留，但每条规则只有一个正文归属。

页面分四层：

- **最小入口**：`SKILL.md` 只保留触发、边界、模式、核心事实契约和交付形态。
- **路由入口**：`reference-index.md`、`genre-routing.md`、轻量任务卡只选路和停止，不写完整骨架。
- **能力与文种叶**：共性能力各自唯一归属，文种叶各自承担文种功能、结构和状态边界。
- **执行工具**：脚本负责可观测检查，Hook 负责用户明确要求的宿主门禁；二者不负责文种选择。

## 3. 规则重写原则

- 先读懂旧 `SKILL.md` 和全部 reference，再建立“旧规则→新模块”的语义映射；每条可执行语义必须保留、迁移或有明确废弃理由。
- 文种叶只写本身的功能和结构；事实选择、办理要素、论证、结构修改、字段修改、压缩、反旁白、校对和格式分别由唯一共性叶承载。
- 混杂旧叶改为“一个短分流页 + 必要数量的稳定主叶”。一个叶子混有两三套骨架时拆职责；职责本来单一且已有实证的新叶直接复用。
- 跨文种的固定用语、引叙、承启、敬辞和历史模板保留一个能力页；文种叶只保留本身不可缺的功能性收束和语气。只有同一规则在不同文种确实产生不同动作时才在文种叶写差异，避免复制同一用语表。
- 控制叶子数量和路由复杂度：只有在触发条件稳定、读取集合可观测、正文收益可验证时才新增叶；避免为了字符数把规则切成许多互相跳转的小页。
- 每个路由必须写出触发信号、首叶、允许叠加、不应加载的相邻页、停止点和升级条件；避免引用环。
- 规则优先使用正向动作：写什么、保留什么、按什么顺序、何时转读。只有安全边界无法正向表达时才用“不得/不补”等限制，并避免连续否定堆叠。
- 保留新旧文种的质量衔接：旧文种叶中已验证的事实状态、称谓、主体关系和交付形态不能因重写变弱；新叶不应被旧总页再次污染。
- 过程旁白、正文外制作说明、Markdown 包装、教学式解释和用户未要求的自证属于交付风险，应在规则和脚本结果解释中明确压制，但不把脚本提示机械升级为文种硬门。

## 4. 已知混杂债务的处理

- `genre-checklist.md` 改为未覆盖文种的功能反查页，不再集中承载多个文种完整骨架。
- 算力不作为文种。主文种先按报告、方案、采购或技术材料路由，再在算力相关稿件上叠加唯一的 `ai-compute-docs.md` 场景附加叶；术语和示例按需叠加。
- 当前附加叶复核见 `maintenance/docs/reference-overlay-review-20260912.md`；讲话人物顺序是另一项局部附加能力，新闻消息和新闻评论仍是独立文种页。
- `task-route-cards.md` 只判断能否走轻量路线，不承载会议、通知、报告或局部修改的专属规则。
- `genre-routing.md` 只判文种、行文关系和冲突，不重复专页骨架。
- `workflow.md`、`final-review-layers.md`、`review-checklist.md`、`anti-ai-patterns.md`、`proofreading-checklist.md`、`handling-elements.md`、`argument-chains.md`、`information-selection.md` 重新建立唯一职责和共享契约。
- 已验证的新叶（新闻、新闻评论、意见建议、投诉反映、整改、增项申请、制度、通知公告、部署、函、纪要、讲话、研究、采购、人物顺序及兼容场景）优先复用语义，重新接入新路由，不做无收益重写。

## 5. 脚本与 Hook 要求

- 现有 `prose_lint.py`、`review_gate.py` 及相关命令代码优先复用；只改必要的调用入口、参数说明、结果解释和测试绑定。
- 脚本只提供语言、格式、结构、交付洁净度等风险提示；不得自动改写，不替代文种完整性判断，不把偶发模型输出变成硬门。
- Hook 目录保持零产品改动；重写后的 Skill 只规定何时显式读取 Hook 入口，不复制 Hook 内部规则。
- 五条便宜模型通道使用客户端实际显示名称；测试优先 `max`，技术失败再记录高强度回退。真实写稿测试必须绑定新 provider 配置。

## 6. 真实写稿验收

候选与当前 main 使用相同提示、相同模型通道和相同输出要求，按单叶、二叶组合、跨文种和脚本/Hook 边界分组测试。至少覆盖：

- 稀疏情况说明、短通知、报告、请示/申请、函、纪要、讲话和人物开场；
- 方案、研究/可研、采购审查、算力可研、算力采购/租赁、算力技术需求；
- 新闻消息、新闻评论和兼容场景；
- 局部结构修改、字段修改、长文压缩、只审不改、综合复核、Word 正文和脚本调用；
- 过程旁白、空行、Markdown 残留、状态升级、主体关系、日期和数字保真。

每稿记录：实际读取页、首叶和停止点、正文事实/数字/日期/主体/状态、文种功能、输出形态、旁白与格式、脚本调用和技术结果。

排除因素：

- 两臂同样出现的措辞长短、模型随机性、通道延迟和共有工具失败归为模型/环境波动；
- 只在候选出现且能归因于新规则或新路由的事实、状态、文种、格式或必要内容损失，才记候选回退；
- 门禁过严导致的失败与正文质量分开记录，不以单次门禁失败直接否定路由；
- 脚本未被宿主调用只记可观测性，不冒充正文质量收益。

## 7. 合并标准

只有同时满足以下条件才允许合并：

1. 旧规则语义均已归位或有明确保留/废弃记录；
2. `SKILL.md`、references、脚本说明和镜像通过静态工程门；Hook 目录与基线无差异；
3. 真实写稿中候选无候选独有硬回退；
4. 目标任务的无关 reference 伴读确实减少，且首叶、组合和停止点稳定；
5. 新旧文种质量衔接不劣于当前 main；
6. 旁白、空行、措辞变化按归因结果判断，不能把正常模型波动当作规则回退；
7. 证据足够支持合并后，才在独立分支提交并合入 main；未经另外授权不推送、不发布。

每个重写批次必须记录目的、涉及页面、保留语义、删除/迁移语义、静态测试、真实写稿结果、已知风险和下一批边界。产品版本和平台发布另按用户明确授权执行。
