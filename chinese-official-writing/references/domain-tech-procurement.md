# 技术需求、AI 算力、信息化、采购验收与软件正版化

本页作为专业领域附加规则（独立技术需求可直接作主叶；其余场景在已选主文种上按需取用对应章节，不改变原主文种用途）。

---

## 一、技术需求书与需求附件

- **骨架**：`需求对象与用途 → 功能、资源或服务范围 → 接口与运行条件 → 交付与技术支持 → 验收要求`。
- 使用可度量、可检查的“应支持/应提供”表述，拟提要求与现有能力分开；接口写清对接双方、数据方向与输入输出，具体协议、性能数值与安全等级以材料或授权为准，不凭业务名称推定技术实现。
- 交付与运维保持工作与承担主体对应；只有功能需求时不补合同付款、人员资质或固定运维承诺；验收项目与本次需求逐项对应。

## 二、AI 算力专项（仅限算力/推理训练/智算中心/模型服务资源）

- **需求与指标口径**：区分当前实际用量、受限使用及原因、未来范围与增长假设。Token 用量及单价用于费用测算；TOPS/TFLOPS 表示算术吞吐能力（须带精度口径）；业务承载能力须结合模型、输入输出长度、并发与响应条件判断，引用测评保留原条件。
- **路径与成本比较**：云端 API、购置自建、GPU/服务器租赁、本地化部署按同一服务期、需求规模与计费口径比较（现金支出、部署运维、数据审计控制、连续性冗余、统一调度）；成本章节写清需求来源、服务期、资源覆盖与费用边界，除非用户要求测算表，不把正文写成“单价×数量、计算如下”的计算草稿。
- **SLA、安全与验收**：SLA（可用性、故障响应/恢复、峰值并发与排队、资源隔离、监控日志、版本切换）与安全（数据类型、权限密钥、审计范围）按材料落位，未给阈值时不代拟合同条款，无区域/等级/厂商依据时不外推合规结论；验收对应规格、并发测试、可用性、日志安全与运维文档。
- **常用术语译法**（材料无另行指定时首次按需附全称，后文统一缩写）：`图形处理器（Graphics Processing Unit，GPU）`、`应用编程接口（Application Programming Interface，API）`、`服务级别协议（Service Level Agreement，SLA）`、`数据中心电能利用效率（Power Usage Effectiveness，PUE）`；产品/模型名保持官方拼写，含义不明内部缩写不自行展开。

## 三、信息化建设与运维

- 写清既有系统业务、痛点与本次新建、复用、升级、整合或维护的范围；系统对接交代对象、数据来源与权限。
- 升级/替换/整合项目交代数据迁移、原系统衔接与运行过渡安排（对象与数量对应）；分清一次性建设费用与持续运维服务期，区分交付、试运行、验收与运维阶段。

## 四、采购专项核对

- 核对品名、规格、数量、预算/单价、报价覆盖内容（安装/运输/税费/授权/维保及期限）、响应规则与验收归档。
- **报价与总额核算铁律**：算单价×数量前先确认是否覆盖同一范围——结果公告的“主要标的”未必涵盖整包，未确认范围的差额仅提示核对，不判总额错误或强求补全清单；同范围算术差异须回溯原始报价再定改值；服务费按既有收费依据核对，反推费率仅作待核假设。预算控制价与询价报价分布明显不匹配（如仅一家报价低于控制价、可能影响竞争性磋商或招标法定响应家数）且交付允许提示时，在稿外简要提醒核实。
- **口径与状态**：只有预算数值不写成“经测算”；采购需求本身不等于已有故障损失；供应商/采购日未定时保留核心未定状态即可，**删除由它顺带拖出的“合同未签、未到货、未验收、未付款”等冗余下游否定链**。

## 五、项目与采购验收

- 按交付用途与行文关系选主叶：**申请组织或批准验收走请示/申请（不相隶属间用函），通知参加验收或征集验收材料走通知/函**，汇报验收情况走报告，独立专家/验收组意见走审查意见，有权机关审批答复走批复/函，公开结果走公开发布（验收公告不转采购征集公告）。
- 锁定项目、合同及本次验收范围；**合同总额与本次验收金额分别标明**；分清到货、安装调试、试运行、质量核验与有权主体验收结论；采购人代表、验收组、专家、供应商记录各自归属，保留“同意验收/原则通过/附条件”原程度及验收日期与发布日期的区分；**保留意见、整改和复验要求须逐项挂接到其影响的具体验收项**。

## 六、软件正版化与许可管理

- 按原口径交代设备、安装、账号、订阅与场地授权，名称、数量、来源、期限和适用对象逐项对应；预装、附带系统与集团统购按实际随附/分配关系写。
- 采购付款记录、供货方声明、许可范围与独立核验结论各按其证据写；个人订阅、免费或开源工具注明版本与许可范围；许可范围缺记时在该条目交代已有授权记录。涉及对外提供正版工具时写清按授权获取方式及业务用途，自研与第三方技术、专利申请与授权各守实际阶段。
