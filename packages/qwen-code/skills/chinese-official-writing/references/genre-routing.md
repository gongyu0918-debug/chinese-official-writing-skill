# 文种路由

本页只解决“这份材料应该按什么功能写”。确定文种后，转入对应专页；本页不复制各专页骨架。

## 判定树

用户只说“会议通知”“采购申请”等事务名称时，仍先建立可执行的事务首叶：会议通知归通知，采购申请归申请/请示。缺少规范标题不等于无主路由；只有合作性意见建议、投诉反映等不承担正式行文关系的材料，才转入兼容场景叶，并保留必要的事实、字段和交付检查。

### 1. 先看用户交付对象

- 用户给了模板、最新版底稿或明确标题：先保留其结构和对象，再检查正文功能是否匹配。
- 用户只说“写材料”：从办理对象、行文关系、是否需要审批和是否面向公开范围判断。
- 一份任务包含通知壳、附件方案或附件制度时，先分开处理，不把附件标题当成主文种。

### 2. 再看行文关系

- 上行：向上级汇报、反映情况、请求指示或批准。对应报告、请示、上报申请、可研附件等。
- 下行：向下级或一定范围部署、告知、批评表扬或作出决定。对应通知、决定、通报、批复等。
- 平行：不相隶属单位之间商洽、询问、答复、征求意见或请求支持。对应函、复函、征求意见函。
- 公开：面向社会或一定范围公开发布事项。对应公告、公示、通告、公报、新闻消息。
- 发言：特定身份在会议、活动或仪式上表达主题、观点、部署或期望。对应讲话稿、致辞、演讲词。
- 会议主持：按已给会议议程引导环节、发言、程序和转场。对应会议主持词、主持串词。
- 述职：个人或班子向考核、评议或管理主体报告职责履行情况。对应书面述职、述职报告、履职情况报告和现场述职发言。
- 会议记录：会议纪要按会议讨论和形成的事项选路，不预设为上行或下行；分发对象、责任主体和期限沿用材料。

### 4. 处理容易混淆的边界

- 报告只汇报或反映，不把结尾写成请批语；需要批准时转请示或上报申请。
- 工作总结以回顾和经验归纳为主，文内下一步安排继续按总结组织；独立工作要点以前瞻任务为主。周报、月报沿用报告主叶的周期形态，不因有下周或下月安排改成工作要点。
- 标题为“情况说明”时按实际用途选路：解释具体事实、原因或回应疑问转说明主叶，汇报工作进展、问题或处置转报告主叶。
- 请示聚焦一个请批事项；成绩和背景只保留支撑该事项的事实。
- 通知写办理要求；活动已经发生且面向公开传播时转新闻消息。
- 纪要记录会议形成的事项；未形成决定的讨论内容保持建议、待评估或下次再议状态。
- 公告面向较广范围公开宣布，公示强调期限和异议渠道，通告强调一定范围内应知或应遵事项。
- 函保持平行商洽语气；批复是上级对下级请示的正式答复。
- 方案写行动路径；可研写决策依据和比较；采购公告、征集公告和采购事项告知优先转 `genre-playbook-procurement-announcement.md`；审查材料写发现、风险和整改程序。
- 新闻评论可以提出判断，但判断和材料中的事实、决定、责任安排分开。
- 主持词组织会序；主持人另作的主题讲话、点评或总结发言按实际功能处理。会议纪要记录会后形成的事项。
- 述职围绕报告主体及职责；现场述职发言与书面述职共享履职内容，单位工作报告或工作总结按各自主文种处理。

## 混合材料的处理

1. 先确定用户要交付的主文本。
2. 将其余内容标为附件、背景、引用事实或待核材料。
3. 主文本只承载自己的文种功能；附件另按对应专页处理。
4. 标题与正文功能冲突时，保留用户标题是否可改的约束，在正文中按真实功能成稿。

## 路由结束

文种和行文关系确定后，读取上表对应专页。尚无法判断的用途集中向用户确认。
