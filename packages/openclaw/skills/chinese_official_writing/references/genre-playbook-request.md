# 请示/申请 Playbook

本文件用于请示、申请命中常规或完整骨架时直接进入对应文种规则。

## 使用方式

- 路由已确定为请示或申请后进入本文件；工作流、事实选择和文种冲突按已命中的共性页处理。
- 用户已有模板、称呼、字段顺序和落款方式优先；本文件只确定文种骨架和风险点。
- 事实、状态和缺项统一按 `information-selection.md` 处理。

## 请示/申请

请示用于请求上级指示或批准，一文一事并落到请批事项；申请保留原因、依据与申请事项。主送采用用户给出的接收对象，机关名、部门名或职务称谓均按材料使用；落款采用已给的发文或申请主体，具体位置服从用户模板。

- 适用：向上级、领导班子或审批方请求批准经费、事项、资源、立项、采购方式。
- 骨架：请示通常按请示缘由、请示事项、请示要求组织；申请必须有能够成立的原因、依据或必要性，通常在正文前部先交代，再落申请事项、方案/金额/资源、当前状态和请批语。请示和申请的紧凑短稿均可在同一句中承载缘由与事项，不要写成只换述请求事项的无理由短句。
- 风险：请示一文一事；申请保留用户模板和称呼，文种根据用途判断。“妥否，请批示”可用于相应的申请。未给的主送、申请单位和日期按 `information-selection.md` 核对缺项，正式成稿清理无用途的占位。
- 材料已经给出原因、现状压力或制度依据，或已给事实与常识能够直接支持一般必要性、直接用途时，在请示或申请事项前用一层低强度表述自然承载。完全无法闭合时，视为实质缺口；输出允许正文外提示时，只短列需要补充的缘由、依据或用途，不顺带罗列主送、日期、附件、流程等其他缺口；只交正文时不夹带说明，也不留空白横线或“事由待补”等占位。
- 单项采购请示或申请用一至两个自然段连贯呈现原因或必要性、品名规格、数量和金额。现有资源数量、使用负荷、排队共用、已确认损坏等事实可归纳为缓解对应压力或满足直接使用需要；只有品名、数量和金额而无法判断为什么采购时，按上条提示缺口。不得补具体故障、损失、政策条款、采购程序或审批结论。多品类、分项核算、比价验收、技术附件或明确长篇任务仍以本页为主文种；需要核对主体、金额、期限、附件或反馈时加读 `handling-elements.md`，需要解释必要性或比较方案时加读 `argument-chains.md`；字段表格保持原结构。
- 请假申请一般写明假别、事由或制度依据、起止时间和已给交接安排。年休假、婚假、产假等依规申请的假别，可在申请事项前使用“根据有关休假规定”等不特指条款的一般依据，不强行编造个人私事原因；事假、病假等完全未给具体事由时，不用“因个人事务”“因身体原因”等泛称代填。材料只给工作交接时，不据此补“工作不受影响”、通讯承诺或代办责任。
- 材料只写设备老旧时，不推成运行缓慢、性能不足、影响服务或群众体验；材料只写采购正在推进时，用一句保留当前状态，不补依法依规、预算控制、采购流程、完成承诺、效能提升或后续环节。材料只写供应商尚未确定时，正文停在该状态，不补确定后或批准后如何采购、报告、到货、验收、付款。事实不足以撑满字数下限时，按 `information-selection.md` 短而完整地成稿。
- 需要论证或称谓复核时，结合 `argument-chains.md` 核对依据与请求之间的关系和 `formal-addressing.md`。
